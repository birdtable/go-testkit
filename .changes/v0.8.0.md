## v0.8.0 - 2026-11-26

One check is added to `canary`: `(*Set).Expect(name, paths...)`, for a value a program must keep in named files of a folder, an app's own secrets file among them, with `(*Expected).Expect` for another value and `(*Expected).Files(dir)` to check the folder. What it excuses is narrow: the value, in any encoding, in the bytes of a path named for it, and nothing else. An expected path that does not hold its value fails the test; a hit of the value anywhere else in the folder fails, in any encoding, in any other file or a link's target; any other value in the expected file fails; and the value in the expected file's own name, or a folder above it, fails. A path that names nothing, a folder, a link or no regular file fails the test, and so does an expected file that is not, when open, the file the walk saw there, as when a link is swapped in for it; a path that is absolute, names a drive or a share, or leaves the folder stops the test. `Zip` does not take `Expect`, nor do the Set's own `Files`, `Reader`, `Bytes` and `Value`, which excuse nothing. Four names are added: the type `Expected`, `(*Set).Expect`, `(*Expected).Expect` and `(*Expected).Files`. No name is removed or moved, and no signature changes: the API check finds no break since v0.7.0. Every name added is experimental, as every name of the module is. `canary` still imports the standard library only, and the root's go.mod still requires nothing. contain stays at contain/v0.1.3 and taskfile at taskfile/v0.1.2: nothing in either module has changed since v0.7.0, and since contain/v0.1.3 contain's api/systems.txt and api/marks.txt change in their comments alone. The tagged tree is 7,648 non-test Go lines outside `internal/` (`task size`), at its ceiling of 7,648, up 129 from v0.7.0's 7,519 (1.7%), all in `canary`, now 867: 118 for Expect, and 11 for the check that an expected file is the one the walk saw. The full release checks ran on macOS (arm64) at the tagged commit; vet and the tests, with the race detector, ran on Linux, macOS and Windows at the tagged commit in CI. No full release checks ran on Linux or Windows for this release.

### For a v0.7.0 caller

A test that passed at v0.7.0 passes at v0.8.0: `Files`, `Zip`, `Reader`, `Bytes` and `Value` check as they did, and only a test that calls `Expect` meets anything new. A test that scanned a copy of its folder with its secrets file taken out, because `Files` failed on it, can check the folder itself with `s.Expect("token", "secrets.json").Files(dir)`.

### Added
* canary: `(*Set).Expect(name, paths...)` is a check of one folder in which a planted value must be, an app's own secrets file among them, and its `(*Expected).Files(dir)` checks that folder as `Files` does but for one thing: a hit of that value, in any encoding, in the bytes of a path named for it is no failure. Each path is relative to the folder, cleaned, and names one regular file, with no globs; `(*Expected).Expect` names another value, so one file may hold more than one. What it does not excuse: the value in the expected file's own name or a folder above it, in a link's target and in any other file, in any encoding, and any other value in the expected file, are hits as before. A path that names nothing, a folder, a link or no regular file fails the test, and so does a path whose bytes do not hold its value in any encoding, so no check passes because a path was named; an expected file that is not, when open, the file the walk saw there, as when a link is swapped in for it, is not read and fails the test; each line names the path and the value's name, never the value. A name never planted, no path, a path that is absolute, names a drive or a share, or leaves the folder, and a path named twice for one name stop the test. Only `(*Expected).Files` takes an expectation: the Set's own `Files`, and `Zip`, `Reader`, `Bytes` and `Value`, excuse nothing.
